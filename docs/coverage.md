Check current [Workers runtime APIs](https://developers.cloudflare.com/workers/runtime-apis/) and product docs **per row** before implementing. Pin these dependencies *in this project* before treating their declarations as compile targets.

Legend for test columns: `L` = local Miniflare/workerd integration (not merely a mock), `M` = real C++/Wasm dispatch with an explicitly mocked provider (not native-binding or service evidence), `V` = isolated opt-in live Cloudflare integration, `N` = native C++ unit/contract test, `partial` = only a named subset works, `—` = not meaningful/available (explain with evidence). This is a prospective plan, not completed evidence. Every advertised method needs explicit success and applicable failure cases. Preserve source line references when updating the target version; no global platform-parity claim is implied.

## Verification rules

1. Start with W01–W02 and X01 feasibility: compile actual C++, import Wasm in module Worker, validate async/lifetime and compare cold start/bundle size. Rust `worker-build --emscripten` is not a C++ compiler pipeline.
2. Before binding an ID, compare the pinned project's TS types/config against the current [Workers binding docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/) and note compatibility flags, account restrictions, and a precise method checklist in its example README/test. Feature categories above compress signatures; implementation and test coverage are counted at **operation** granularity, not by module name.
3. L requires invoking real local runtime binding, not just JS mock or typechecking. V requires live account resource and verifiable output. Unavailable capabilities remain `—` with a cited limitation, not a passing test; live suites opt-in and must clean test resources without touching user resources.
4. Never count a product accessible only by REST/API or dashboard as a Worker binding. Track future changes through a separate source/version refresh. Bundle size, overhead, errors, resource isolation and cleanup are release gates.

## Bazel-built live re-verification

The [2026-10-14 Durable Object rerun](live/bazel-durable-2026-10-14.json)
passed from clean source `79c2349`: per-object initialization, concurrent increments,
SQL readback/isolation, transactional rollback, binary HTTP/SQL, error guards and
real alarm effects. Worker, namespace, DNS and certificate cleanup were verified.
This is new Bazel-built evidence for the existing subset, not a claim of forced
live eviction, alarm retries or full platform parity. Other historical live results
retain their original provenance until individually rerun.

The [Bazel-built WebSocket rerun](live/bazel-websocket-2026-10-14.json) also
passed text/binary echo, durable state, client/server close, handler failure,
frame limits and upgrade guards. The persisted initialization counter advanced
from 1 to 2 while the same socket survived the idle interval: reconstruction was
observed, not forced or guaranteed. Worker, namespace, DNS and certificate cleanup
were verified independently.

The [Bazel-built Queue/Cron rerun](live/bazel-events-2026-10-14.json) passed
text/binary delivery, explicit retry/redelivery and oversized-message rejection.
The overall probe **failed** because no durable Cron write was observed; the CLI's
reported schedule application is not delivery evidence. Queue batch sending was
not covered by this live probe. Consumer, Worker, queue, D1, DNS and certificate
cleanup were verified. Cron remains unresolved rather than classified as an
unsupported platform capability.

The [Bazel-built clock rerun](live/bazel-clock-2026-10-14.json) passed f64
Unix milliseconds, 33 equal synchronous production samples, post-I/O samples,
JS before/after brackets and eight concurrent requests. Worker, DNS and certificate
absence were verified after cleanup. Local workerd instead reads the system clock:
its tests check each sample against JS brackets, not production-only freezing.
Neither test path establishes precision, monotonicity or synchronization.

The [45-minute Bazel JS/C++ Cron control](live/bazel-cron-control-2026-10-14.json)
observed no durable writes from either implementation. Both schedule PUTs were
captured with HTTP 200; enabled invocation logs and full-window, exact-name
telemetry queries supplied no delivery evidence. Both Workers and D1 were
independently verified absent after cleanup. This is an unresolved account/runtime
verification gap, not a successful live handler test or an unsupported-platform
classification. Email live verification still requires approved sender/destination.
